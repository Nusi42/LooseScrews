# Milestone 5 — Platforms and ops

Status: **draft, pending review**. Nothing here is accepted yet. Every design decision below is a *Proposal*, and the open questions are in §8 · Design source: [design/game-design-doc.md](design/game-design-doc.md) (Tech architecture: Rendering, Networking, Bandwidth for 32 players, Servers; Monetization for the desktop app) · Previous milestone: [milestone-4-plan.md](milestone-4-plan.md) · Overall plan: [implementation-plan.md](implementation-plan.md)

Milestone 5 takes the game from "runs on the developer's machine in Chrome" to "runs on more machines, and other people can run it". The design doc calls for:
- a Tauri desktop app with a UDP transport;
- a WebRTC fallback for browsers without WebTransport;
- a WebGL2 fallback for browsers and GPUs without WebGPU;
- regional server deployment through an orchestrator (Agones or Nomad);
- bandwidth optimization for 32-player matches.

M5 also takes over every carried-over item that [implementation-plan.md §8](implementation-plan.md#carried-over-items) schedules into M5: the bandwidth worst case, the exact lag-compensation view tick, hosted CI (declined), wall-clock tick timing, the Chrome `powerPreference` warning, reference mid-GPU timings, and the kill-cam after your own death. It also takes the security and robustness gaps found in M3, and the M4 exceptions and leftovers.

Requirements taken before planning:
- The standing bar for everything visual: the first impression must be strong. This applies to the WebGL2 look and the desktop app as much as to new effects. Every package that draws something adds gallery scenes and sends before/after shots for the phone review.
- Browser automation stays headless and injects `tools/browser-smoke/fake-pointer-lock.mjs` on every page, scratch scripts included. That covers the WebGL2 gallery, the WebRTC smoke and anything that drives the desktop app's web view.
- M4 closed with the own-death kill-cam moved here under the §7 cut order. That cut was not confirmed, and the grumpy mood's extra cave-ins were not decided either. Both are planned as small first-wave items (question 11).

## 2. Current state (start of M5)

- **Transports.** Browsers connect over WebTransport (UDP, `wtransport` 0.7, self-signed ECDSA certificate trusted by hash from `GET /cert-hash`, 13 days, rotated every 6) with a WebSocket fallback (`web/src/net/connect.ts`, `transport.ts`, `webtransport.ts`; `?transport=ws|wt`). Both feed one `Hub`, so rooms never know the transport. There is no WebRTC. `ls-bots` has native WebSocket and WebTransport clients (`crates/ls-bots/src/transport.rs`), the only native client code in the repo.
- **Secure context.** WebGPU *and* WebTransport need a secure context. A page opened as `http://<LAN-IP>:7777` shows the "needs WebGPU" error screen (`web/src/ui/errorScreen.ts`), not only a WebSocket fallback. Public hosting therefore needs HTTPS with a real domain: the hosting guide documents a Caddy reverse proxy.
- **Renderer.** WebGPU only, about 19,000 lines in `web/src/renderer/` (TS including the shader builders; about 4,200 lines of WGSL builders in `shaders/`). It has two compute pipelines (the light froxel masks in `lights.ts` and the rock texture generation in `rockTextures.ts`) and storage buffers read in fragment shaders (the light masks). It renders into `rgba16float` with MSAA 4x, uses `timestamp-query` when present, and selects quality presets high/medium/low automatically. `initGpu` (`gpu.ts`) throws `GpuUnavailableError`, and there is no other backend. Gallery: 173 scenes. Integrated-GPU floor (M4 D5, Radeon 2 CU, 1080p high): median 24.7 ms, p90 60.2 ms, sunlit caves about 60 ms.
- **Server.** `ls-server` serves static files, `/ws`, `/cert-hash` and the `/api/...` JSON API on one TCP port, and WebTransport on UDP. It has no health or metrics endpoints (only `tick stats` log lines), handles only Ctrl+C (no drain), and has no TLS for HTTP. `ls-directory` is plain HTTP, in-memory, with per-IP rate limits but no forwarded-for handling. Tick times are wall clock (`stats.rs`).
- **Machine and repo.** Development and every recorded run are on Windows 11 (Ryzen 9 9950X3D, shared). There is no Docker, no WSL distribution, no Nomad, no `gh`; the Rust targets installed are the Windows ones and `wasm32-unknown-unknown`. The repo has no hosted remote: `origin` of the work folders is the local master.
- **Bandwidth.** 32 busy ships with about 100 projectiles in flight: whole deltas average 392-405 / 476-491 / 544-560 B against 2 / 4 / 6-tick baselines (budget 576 B per snapshot). The busiest reach 471-482 / 565-612 / 614-683 B. New projectiles are about 10 B each, mostly a 43-bit velocity residual and a 28-bit position residual. No live room has had more than 8 bots (plus Welcome probes).
- **Lag compensation.** The shooter's view tick is estimated from the acked snapshot (under one tick of error on average; game-glue.md).
- **Identity and lobby.** No accounts. A browser keeps a public id and a private token. Presence comes from `POST /api/presence` polls, not from the game connection. `/api/duel/answer` and the party `player` tag take no token, and the roster lists any id that polls.
- **Versions.** Protocol 6, `SIM_BEHAVIOR_VERSION` 6, rule set code format 5, generator version 4, `REPLAY_GOLDEN_HASH` `0x6d20_19b0_f52b_3f3f`, the nine mode replays and the 25 mood replays (`crates/ls-sim/tests/fixtures/mood_replays.txt`).

Every row is a *Proposal* until it is accepted. Rows that are rejected or changed are updated here before the wave that needs them starts.

### 3.1 Desktop app (Tauri)

| Topic | Decision |
| --- | --- |
| Shape | *Proposal.* Tauri 2. The app shows the bundled web client (`web/dist`) in the system web view: WebView2 on Windows, which is Chromium, so WebGPU and the whole client work as in Edge. The game core stays the WASM build inside the web view (question 5): there is one client code path, no new determinism surface, and no per-frame IPC of chunk meshes. The design doc's "native build of the core" becomes a later option, which the native = wasm32 golden checks would cover |
| Folder and build | *Proposal.* `desktop/` with its own Cargo workspace (`desktop/src-tauri`, excluded from the root workspace), so `cargo test --workspace` does not compile Tauri and its web view crates. `desktop/package.json` holds `@tauri-apps/cli`. Builds go into `CARGO_TARGET_DIR=target/pkg`, like every package. A Windows-only `tools/ci.*` step builds it (`LS_SKIP_DESKTOP=1` skips it) |
| Network bridge | *Proposal.* Rust commands `net_connect(url, kind)`, `net_send(bytes, reliable)` and `net_close()`, plus a Tauri `Channel` that pushes received packets to JS. On the web side, `web/src/net/tauri.ts` (`TauriTransport`) has the same surface as the other transports, and `connect.ts` picks it inside the app. The native clients come from `crates/ls-netio`, moved out of `ls-bots` (WebSocket and QUIC/WebTransport with trust by certificate hash; later WebRTC, §3.2). The app never needs the browser's secure-context rules, so it also reaches LAN servers on plain addresses over UDP |
| Native transport | *Proposal* (question 4): QUIC datagrams through the existing WebTransport endpoint. That is UDP, encrypted, and needs no new server endpoint. At 30 snapshots a second (about 18 KB/s) QUIC's congestion control never limits the datagrams, so the latency equals raw UDP. The C2 package measures round trip and jitter for raw WebSocket, browser WebTransport and the app's QUIC on the fleet simulation. A raw UDP protocol (stateless-cookie handshake, ack bitfields, reliable fragments) stays a fallback if the measurement shows a gap |
| HTTP from the app | *Proposal.* Server list, directory and `/api` calls go through a Rust HTTP command when the web view would block them (mixed content, CORS). The app's origin is a local secure origin, so WebGPU works |
| Identity and settings | *Proposal.* The same anonymous public id and private token as the browser, kept in the app's data folder (no accounts, question 8). Settings stay in the web view's storage |
| Window | *Proposal.* Title, icon, a remembered size, F11 fullscreen, pointer lock (Chromium's, inside WebView2), no browser chrome. A strict CSP. The IPC allow-list holds only the bridge and HTTP commands. No remote content is loaded |
| Packaging | *Proposal.* An NSIS per-user installer (no admin rights) with the WebView2 bootstrapper, and a portable zip. Target size under 30 MB |
| Updates and signing | *Proposal* (question 6). The Tauri updater plugin is wired but off until an update URL and the updater's public key are configured; the private key stays with the maintainer, never in the repo. Code signing is a CI step that runs only when signing secrets exist. M5 builds are unsigned: testers click through SmartScreen, as the player manual will say |
| Deep links | *Proposal* (first in the cut order). `loosescrews://join?...` opens an invite link in the app. The browser's invite page offers "Open in the app" when the app is installed |
| Testing | *Proposal.* Headless rules apply. The bridge has an integration test against a real `ls-server` on `127.0.0.1` (no window). `TauriTransport` has unit tests with a fake IPC. A desktop smoke starts the built app with a window that is never shown (`--smoke`): the fake pointer lock is injected through Tauri's init script, the app connects to a local server, flies 20 s of scripted input, writes a JSON report and exits. If WebView2 does not render in a hidden window, the smoke checks the connection and the session only, and the maintainer's own install-and-play test covers the rest |

### 3.2 WebRTC fallback

| Topic | Decision |
| --- | --- |
| Who needs it | *Proposal.* Browsers without WebTransport, or networks that block it, still get an unreliable channel instead of TCP head-of-line blocking. WebRTC also works on plain-`http://` pages, which together with WebGL2 makes LAN play over `http://<LAN-IP>` work |
| Server | *Proposal.* `crates/ls-server/src/rtc.rs` on `str0m` (sans-IO WebRTC, which fits the poll-based `Transport` and the tokio socket tasks), checked by A5 to build on Windows and Linux without system OpenSSL and within `ls-server`'s MSRV 1.88; `webrtc-rs` is the alternative. ICE-lite with host candidates from `--public-address` (or `--rtc-public-ip`), and no TURN (WebSocket covers TCP-only networks). UDP on `--rtc-bind` (default: game port + 1), `--no-webrtc` to turn it off |
| Signalling | *Proposal.* `POST /rtc/offer` on the game port: an SDP offer in, an answer out (one round trip, ICE candidates in the SDP, rate-limited per IP, at most `--max-players` pending sessions) |
| Channels | *Proposal.* Two DataChannels: `unreliable` (unordered, `maxRetransmits: 0`, messages up to 1200 B like the datagram limit) and `reliable` (ordered). The first reliable message is `Hello`. Both feed the same `Hub` and `SimLink` as WebSocket and WebTransport |
| Client order | *Proposal.* WebTransport (when the browser has it and `/cert-hash` offers it), then WebRTC (when `/rtc/offer` answers), then WebSocket. `?transport=rtc` forces WebRTC, and the F3 overlay names it |
| Ports | *Proposal.* The hosting guide's firewall table gains the WebRTC UDP port. `tools/check-binds.mjs` keeps every test on `127.0.0.1` |

### 3.3 WebGL2 fallback

| Topic | Decision |
| --- | --- |
| Target look | *Proposal* (question 7): **gameplay parity, reduced look**. Everything that carries information is there and readable: terrain with materials, paint and surface states, ships, projectiles, pickups, team colours, mode objectives, event telegraphs, wells, radiation, the ink look of monochrome levels (grey against pigmented ships), HUD. Expensive optional passes may be missing or simpler: volumetric shafts, cloak refraction (a shimmer instead), half-resolution particles, MSAA on GPUs without float multisample targets, fewer lights (16-32). The bar is the WebGPU "medium" look, judged on the phone side by side with WebGPU |
| Approach | *Proposal*, decided by A7's spike. One set of shaders: the WGSL that the TS shader builders produce is translated to GLSL ES 3.00 at build time with `naga` (wgpu's translator, which has a WebGL target), into a generated `web/src/renderer-gl/shaders.generated.ts`, with a `--check` in CI like the player reference. The shader builders gain a `backend` flag for the few places WebGL2 lacks: froxel light masks read from an integer texture instead of a storage buffer, and no compute. A new renderer in `web/src/renderer-gl/` implements the part of `Renderer`'s interface the game calls, so game code does not change. If naga fails on the main shaders, the fallback is hand-written GLSL for a reduced renderer, and the spike records why |
| Compute replacements | *Proposal.* Light froxel masks are computed on the CPU (the same sphere-versus-froxel test, 16-32 lights) and uploaded as an `RGBA32UI` texture. Rock textures are generated once by a fragment pass into the texture array layers (or on the CPU), with the same noise |
| Selection | *Proposal.* `initGpu` failure (no WebGPU, no adapter, no device) falls back to WebGL2. The error screen appears only when both fail. `?renderer=webgpu|gl` forces one, and the F3 overlay shows the backend. The quality auto-step works on GL frame times (`EXT_disjoint_timer_query_webgl2` when present) |
| Reach | *Proposal.* WebGL2 serves browsers without WebGPU: Linux desktops without it, older Safari and iOS versions, Firefox where it does not ship WebGPU yet, blocklisted GPUs and drivers, and plain-`http://` LAN pages. A7 checks the current list against browser release notes and records it in renderer.md |
| Weak GPUs | *Proposal.* B6 makes far terrain cheaper on both backends (fine detail and the second GGX lobe fade out with distance; far chunks shade with fewer samples). Targets on the integrated GPU at 1080p: every gallery scene within 33 ms at "low" on WebGPU and on WebGL2, sunlit caves within 40 ms at "medium". No regression on the RTX 5080 |

### 3.4 Regions, deployment and ops

| Topic | Decision |
| --- | --- |
| Orchestrator | *Proposal* (question 2): **Nomad**. It is a single binary with a `raw_exec` / `exec` driver that runs `ls-server` without containers, allocates TCP and UDP ports, does health checks and rolling updates with a kill signal and timeout, and runs as a dev agent on Windows, so the job specs can be tested on this machine. Agones needs a Kubernetes cluster per region, which is far more than a handful of game servers needs. Nomad's licence (BUSL 1.1) allows running your own game servers. One Nomad region per cloud region, one datacenter each |
| Artifacts | *Proposal.* `deploy/`: Nomad jobs for `ls-server` (per region: count, ports, `/healthz` check, `kill_signal` SIGTERM, `kill_timeout` long enough for a match plus intermission) and `ls-directory`; a `Caddyfile` (HTTPS for the web client, `/ws`, `/api`, `/rtc/offer`, and the directory on its own host or path; WebTransport and WebRTC UDP go straight to the server); systemd units as the no-orchestrator fallback; a Dockerfile as an option. Linux release binaries come from the hosted Linux runner (question 9) or, without one, from a WSL Ubuntu the maintainer installs |
| Ops endpoints | *Proposal.* `GET /healthz` (`200 ok`, `503 draining`); `GET /metrics` in the Prometheus text format (per room: tick p50/p99/max wall and CPU, players, bytes sent per client, full snapshots, matches, rejects, kicks, encode errors; per process: rooms, private rooms free, connections per transport); `--log-format json`. Metrics and health are read-only and carry no player names |
| Graceful drain | *Proposal.* On SIGTERM (Ctrl+Break on Windows) or `--drain-after <s>` (tests), the server stops taking new public joins (`Reject "server draining"`) and leaves the directory. Running matches finish. Players get the results, then a `Disconnect` with the reason "server restarting", and the client offers Quick play. The process exits when its rooms are empty or `--drain-timeout` passes |
| Regions and Quick play | *Proposal.* The directory already carries `--region`. It gains `GET /servers?region=` and a region list. The browser groups the server list by region with each region's best ping. A **Quick play** button on the start screen picks the region with the lowest measured ping (and anything within 30 ms of it), then the fullest public room with space, and moves on to the next region when everything is full. `ls-bots --quick-play` does the same |
| Local multi-region simulation | *Proposal.* `tools/fleet.mjs` starts `ls-directory`, R regions x S servers (each `--region`) and bots on `127.0.0.1`. A test-only `ls-server --debug-latency-ms <n>` (it logs a warning like `--event-schedule`) delays every frame both ways on every transport, so a server "in another region" pings like one: the default fleet is eu +7 ms, us +45 ms, ap +90 ms one way. Quick play, the server list, drain and regional fill are tested against it |
| Real deployment | *Proposal* (question 1): only if the maintainer opens a cloud account and a domain. One EU region on one small VM with dedicated vCPUs, a single Nomad node, Caddy with TLS, the directory and the web client, and a budget cap. Agents prepare scripts and runbooks; the maintainer creates the account and DNS records and keeps every credential. Agents never store credentials in the repo or memory. Otherwise M5 ends with artifacts and the local simulation |
| Directory over HTTPS | *Proposal.* `ls-server --directory-public <https url>`: the URL handed to browsers (presence and `/api/info` replies), separate from the heartbeat URL `--directory`. `ls-directory --trusted-proxy <ip>`: `X-Forwarded-For` is honoured only from that address, so rate limits apply per player, not per proxy |

### 3.5 Server hardening (M3 gaps)

| Gap | Decision |
| --- | --- |
| Duel answers without a token | *Proposal.* `POST /api/duel/answer` takes the answering player's `token`, which must own the challenged id (403 otherwise) |
| Party tags without a token | *Proposal.* Protocol 7 `Welcome` carries a 64-bit `session_key` (from the server's OS random source; never in the sim). `POST /api/party` with `player` must also send that connection's `session_key` |
| Fake presence registrations | *Proposal.* The roster (server list, `/api/players`, challenges) lists only ids with an open game connection: `/api/presence` takes the `session_key` and binds the id to that connection. Presence without a connection still returns the inbox but is not listed. A per-IP cap on presence ids applies |
| Directory address squatting | *Proposal.* The first claim of an address must prove it. The directory answers with a nonce, fetches `http://<address>/api/directory-proof?nonce=` and expects `sha256(secret ‖ nonce)`, and lists the entry only after that. A squatter cannot answer at someone else's address, and an address with no `ls-server` behind it is never listed |
| No backoff for failing next-room builds | *Proposal.* A failing build is retried after 1, 2, 4 ... up to 60 s. After 3 failures the playlist skips to the next entry and warns. Players stay in the running room (results or warm-up) and are never dropped for a failed build |
| A panicked private room keeps its slot | *Proposal.* The room thread runs under `catch_unwind`. A panic frees the slot, sends every link `Disconnect { "room failed" }`, logs at `error` and counts in `/metrics` |
| A join racing a closing private room | *Proposal.* The `Hub` answers `Reject { "room closed" }` (`Reject`'s layout stays frozen) |
| Private rooms ignore `--ban` | *Proposal.* `api::custom_rules` and `duel::duel_rules` resolve rule set codes through the server's `ServerRules` (balance list, then bans), like the public rotation, and the invite shows the effective code |

### 3.6 Bandwidth and lag compensation (protocol 7)

| Topic | Decision |
| --- | --- |
| New-projectile velocity | *Proposal.* A projectile new against the baseline is predicted from its owner: velocity = owner's forward (from the replicated smallest-three orientation, rotated with `+`/`*` only, so native and WASM agree) x the weapon's muzzle speed from the data (the data hash covers it), with the fan index of spread weapons. Only the residual is sent. Fallback per projectile: today's residual against the owner's previous shot, or the raw velocity (2 bits pick). Target: the busiest snapshot within 576 B at 2, 4 and 6-tick baselines on the four seeds of `busy_fight_with_projectiles_fits_the_budget` |
| Exact view tick | *Proposal.* `Input` carries the tick of what the client rendered for remote ships when it sampled the command, as a `u8` offset back from the command tick (clamped to the 250 ms rewind). Lag compensation uses it instead of the estimate, and the estimate stays only as a guard against forged values (the server clamps to what it could have sent) |
| 32 players | *Proposal.* B5 runs the first live 32-player room (31 bots and a probe, Team Brawl) for 10 minutes over WebSocket and WebTransport: CPU tick p99 < 4 ms, per-client average within 17,280 B/s, the busiest snapshot recorded against 576 B, and the `Welcome` size after a heavy 10-minute match. Compression of `Welcome` only if it exceeds 256 KiB |

### 3.7 M4 leftovers

| Topic | Decision |
| --- | --- |
| Own-death kill-cam | *Proposal.* After your own death, the client replays the last 3 s from the killer's view (the victim's view for kills by the level) in the existing kill-cam window, during the respawn wait. It is on by default in modes with respawns (Team Brawl, Paint the Void, Heist, Hot Reactor, runners in The Architect) and off in Belt Up (the hold is short and the course matters), The Squeeze and Last Color Standing. Any key skips it. It never delays the respawn, and the setting is in Options. Client only, no protocol change |
| Grumpy cave-ins | *Proposal.* While the level is grumpy, the cave-in threshold is multiplied by `grumpy_threshold_scale` 0.7 (`data/world/instability.ron`), so cave-ins come about 1.4x as often. Telegraph, safety rules and the 8 s minimum interval stay. The mood is already in the state hash and in `MoodView`, so clients need nothing new |
| Bot stalls | *Proposal.* A per-phase timing log in `ls-bots` (decode, session apply, think: navigation, aim, arsenal, objective; encode; terrain edits), then the fix. Bots send inputs for a new room from its `Welcome`, not from its first snapshot. That removes the transition-window starvation |
| Thin blade steps | *Proposal.* The mesher handles 1.2-2 u blades seen along their thin side (the D5 note: above the thin-rock pass's 0.9 u). Budget +5 % mesh time on sums. Phone review of `cave-sunbeam` |
| Cave-in remesh benchmark | *Proposal.* `crates/ls-game/tests/cave_in_remesh.rs` like `cat_paw_remesh.rs`: p99 per chunk within the client's 4 ms frame budget, measured in thread CPU time (§3.8) |

### 3.8 CI and timing

| Topic | Decision |
| --- | --- |

## 5. Waves

Each wave is a set of packages that run in parallel in separate work folders (`loosescrews.win2`+), one package per folder, as in M3 and M4. Packages in one wave touch disjoint files except under "Shared files"; the integrator (win1) merges them in the listed order. A package may start before its dependency is merged only against the listed day-one contract. "As built" notes are added under each wave during execution.

Rules for every package:
- Build with `CARGO_TARGET_DIR=target/pkg` (the desktop workspace too). The lead deletes `target/` in the package folders after each green wave.
- Browser runs are headless only, with `tools/browser-smoke/fake-pointer-lock.mjs` on every page, scratch scripts included. Automation never shows the desktop app on screen (§3.1 Testing).
- Packages that draw: gallery scenes, before and after runs (`gallery.mjs --label <pkg>-before|after`, `--renderer gl` for the WebGL2 packages), within budget; the lead sends the shots for the phone review after each integrated wave.
- Packages that add a server flag update `--help` and leave the hosting guide to D3. Tests bind `127.0.0.1` (port 0 where possible).
- Credentials (cloud, DNS, GitHub, signing) are never written to the repo, the memory or a package prompt.

1. **Real cloud deployment in M5, or only deployable artifacts and a local multi-region simulation?** If real: which provider, which regions, what monthly budget, and which domain? Proposed: artifacts and the local simulation in any case. A real deployment of **one EU region** (Frankfurt or Nuremberg area, under 15 ms from Berlin as the design doc wants) only if you open the account: one small VM with dedicated vCPUs (for example Hetzner Cloud or DigitalOcean FRA1), a domain of your choice (needed because browsers require HTTPS for WebGPU), and a cap of 30 EUR per month. A US or Asia region waits until there are players there. You create the account, DNS and keys; agents prepare scripts and never hold credentials.
2. **Orchestrator: Nomad or Agones?** Proposed: Nomad. It is one binary, runs `ls-server` without containers, does health checks and rolling updates with drain, and its dev agent runs on this Windows machine, so the jobs can be tested here. Agones needs Kubernetes in every region. systemd units come along as the no-orchestrator fallback.
3. **Desktop app targets: Windows only, or also macOS and Linux?** Proposed: Windows x64 only in M5. WebView2 is Chromium, so WebGPU and every tested browser feature work there. macOS only if you have a Mac (it is needed to build, sign and test; an Apple M1 or newer would also be the reference GPU of question 10). Linux later: its web view (WebKitGTK) has no WebGPU, so it needs the WebGL2 renderer, and testing needs a Linux machine.
4. **The app's "raw UDP": QUIC datagrams through the existing WebTransport endpoint, or a new raw UDP protocol?** Proposed: QUIC datagrams. They are UDP, encrypted, and reuse the server endpoint and the bots' tested client. At our packet rate congestion control never delays them, so the latency should equal raw UDP. C2 measures it, and a raw UDP protocol follows only if the measurement shows a gap.
5. **The app's game core: the WASM build inside the web view, or a native build?** The design doc says "native build of the core". Proposed: WASM in the web view for M5. It is one client code path with no new determinism surface and no per-frame transfer of chunk meshes between Rust and the web view; the app's Rust side does networking only. A native core is a later performance option.
6. **Code signing and distribution of the desktop app?** Proposed: unsigned builds for testers in M5 (SmartScreen warns once; the manual explains it), with the signing and updater steps wired but off. The updater's private key stays with you, outside the repo. Buy signing (Azure Trusted Signing or an OV certificate) and set up a store page (Steam or itch.io, the design doc's Supporter Edition) with the business work in M6.
7. **WebGL2: visual parity, or a reduced look?** Proposed: gameplay parity with a reduced look. Everything that carries information is there; volumetric shafts, cloak refraction, MSAA on weak GPUs and most dynamic lights may be missing. The WebGPU "medium" look is the bar, judged by you on the phone side by side. Full parity would roughly double the renderer work.
8. **Accounts: still none?** Proposed: still none in M5. The anonymous browser (and app) id and token stay, hardened with session keys (§3.5). Accounts come with purchases in M6, where the store needs them.
9. **Hosted CI: may the code go to a private GitHub repository with GitHub Actions?** *Answered: no hosted CI; verification is local (the pre-push hook runs the full check on pushes to the public remote), and releases are built, signed and published locally.* It is needed for the carried "hosted CI" item and is the easiest way to get Linux builds for deployment. Proposed: yes, as a private mirror the lead pushes after each fast-forward of `main`; Linux runners within the free minutes (a few EUR per month if they run out); the browser smoke on a software GPU if that works there. The local `tools/ci.ps1` stays the merge gate. Alternative: no hosted CI, and you install WSL Ubuntu for Linux builds.
10. **Reference mid-range GPU: hardware, or a rented cloud GPU?** No GTX 1660 / RX 6600 / M1 machine was available in M4. Proposed: rent a cloud GPU VM of that class for about an hour after waves B and D (a few EUR each), on the account of question 1. Without it, the timings stay "estimated" with the integrated GPU as the floor.
11. **Confirm the two M4 items for wave A: the kill-cam after your own death, and the grumpy mood's extra cave-ins?** Proposed: yes, both. The kill-cam is on by default in respawn modes and off in Belt Up, The Squeeze and Last Color Standing, and any key skips it. Grumpy levels cave in about 1.4x as often, which is a small gameplay effect of the mood (the M4 plan listed "more cave-ins" for grumpy).
